# M5 — Foundation (Tier 2)

**Primary:** `5` Foundation  
**Does not:** choose a model, download weights, admit a workload,
select serving settings, or start a server

Foundation answers whether this host can hold a Machi-managed native
vLLM environment. The family is `direct`, the engine is `vllm`, and
the executor is `native_process`. NVIDIA CUDA and AMD ROCm are the
concrete providers. They share one resolver, one generation layout,
and one verification contract.

The managed interpreter is Python 3.12, created under
`foundation/generations/<id>/venv`. CUDA installs `vllm==0.18.0` from
PyPI with the torch backend left to the installer. ROCm installs
`vllm==0.18.0+rocm700` from the public ROCm wheel index. A verified
generation is reused. A failed verification is not treated as healthy.
A different pin is a new generation. Historical generations are not
deleted.

The AMD artifact is the `rocm700` recipe: vLLM `0.18.0`, Python
`3.12`, ROCm line `7.0` (not a minimum), glibc `>= 2.35`, and the
sonames actually linked by that wheel and its HIP torch wheel.
Those sonames are versioned (`libamdhip64.so.7`, `librocblas.so.5`,
`libmpi_cxx.so.40`, and the rest of `ROCM700_LIBS`). `libhiprtc` and
`libroctx64` are included because the pinned torch wheel links them.
The compiler SDK, profilers, kernel driver, and firmware are not.
A host may already have that userspace, in which case it is verified
before use. A host with a compatible `amdgpu` line and no userspace
can realize the same recipe under `foundation/environments/<id>`.
The accepted driver lines are `6.2`, `6.3`, `6.4`, and `30.10`.
`6.1` is refused. A missing soname on an existing install is
`prerequisite_blocked` and does not install the wheel. The provider
does not replace the kernel, firmware, or a customer ROCm tree, and
it does not run `ldconfig`.

Inspection is the default and does not install. Provision is explicit
and requires a verified Machi-owned state root. The package cache stays
under that root. System Python is not the runtime. Drivers are not
modified. Prerequisite readiness is consumed when the caller supplies
it; Foundation does not remediate vendor CLIs.

Capacity is consumed and not overruled. The managed Python generation
still uses 12 GiB persistent, 8 GiB transient, and 8 GiB of safe
memory. Those figures are not the managed ROCm prefix. The prefix
footprint is unmeasured, so realization refuses until every required
component has a measured size and that sum fits SAFE storage.
`M-5-AMD-03` records that refusal. If those SAFE values are missing
or smaller, the result is `insufficient_capacity`.

`READY` requires a managed interpreter, a vLLM import, a version that
matches the pin, a backend coherent with the selected provider, and a
discoverable API entrypoint module. Serving remains unsupported.
Streaming is declared by the installed entrypoint and is not verified.
Structured output, LoRA, and metrics stay unresolved.

If native vLLM is unsupported, the result is a typed refusal. No other
runtime is substituted.

`MEANINGFUL_SETTINGS_REMAIN_TYPED_AND_INSPECTABLE=YES`.

Development status is closed. NVIDIA CUDA is physically qualified.
AMD ROCm is implemented and `IMPLEMENTED_UNQUALIFIED`. Do not describe
AMD as production-qualified, commercially supported, or physically
accepted. The deferred proof is `M-5-AMD-01`: qualify the then-approved
AMD native-vLLM recipe on MI300X / gfx942. The historical pin for the
current candidate is `vllm 0.18.0` / `rocm700`. A later approved recipe
supersedes that pin for the gate. It does not rewrite this evidence.

Instance `READY` is not provider qualification. Blocks 6–9 consume
generic Foundation contracts. The qualified development reference is
Linux, NVIDIA, CUDA, native process, managed vLLM.

Tier-3 executors, engines, upgrades, and cleanup are `M-5-01`.
A future OCI image may package the same owned manifest. That builder
is `M-5-AMD-02`. No container runtime is a dependency.
