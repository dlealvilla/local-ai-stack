## Proposed generic seam (not implemented)

```text
AcceleratorObserver                    # generic port
        ↓
NativeAcceleratorObserver              # orchestration in adapters
        ↓
applicable implemented provider(s)     # 0..N; host truth, not a default vendor
        ↓
AcceleratorObservation                 # generic contract
```

Composition (`machi.main`) would wire the native orchestrator the same
way it wires `NativeMemoryObserver`. Domain code would not import
NVIDIA, AMD, Intel, or Apple modules.

Multiple applicable providers must remain possible:

```text
NVIDIA provider → devices
Intel provider  → devices
        ↓
one AcceleratorObservation (device list + provenance)
```

Aggregation is not implemented here. The seam must not forbid it.

Runtime applicability (after implementation):

```text
observe machine
  → determine applicable implemented providers
  → run applicable providers safely
  → combine/return generic accelerator facts
```

No fake provider fallback. Unsupported is not zero. Development
coverage (`build NVIDIA in this increment`) is **not** a runtime
`default_vendor = nvidia`.

## Expected inputs

* Current host environment.
* `OSArchitectureObservation` (family) so orchestration can skip
  inapplicable providers, matching Memory's use of OS family.
* Which providers are implemented and available (PATH/library/OS).
* Optional InstallId / InstallRunId from composition for event
  correlation.

`MemoryObservation` is **not** a required input. Accelerator memory
is a distinct fact. Mixing the two would invite Capacity to
double-count unified memory.

---

## Expected outputs (conceptual; no schema frozen)

A vendor-neutral observation that can represent:

* no accelerator;
* one or many devices;
* heterogeneous vendors on one host;
* vendor and model/device identity without CUDA vocabulary;
* device type (discrete / integrated / unrecognized);
* memory topology: discrete/dedicated, unified/shared, unknown;
* memory bytes **when the source reports them**, else Unresolved;
* observation status and provider provenance;
* unobserved / unsupported / unavailable (not a fake empty rack).

Do not model `GPU memory = always separate VRAM`. Do not compute
usable VRAM, safe accelerator memory, model-fit, reservation, or
available-model sets.

Device identity should not require a PCI bus (Apple Silicon has
none). Where PCI exists it may be compact provenance, not the
generic primary key.

Empty `devices` plus `unobserved`/`unsupported` is not the same as
empty `devices` after applicable providers looked and found none.

## Robustness (conceptual)

| Case | Representable without NVIDIA-shaped fields? |
|---|---|
| NVIDIA discrete, multi-GPU, dedicated memory | YES |
| AMD discrete, no CUDA terms | YES |
| Intel integrated or discrete | YES |
| Apple Silicon unified/shared memory, no invented VRAM | YES |
| No accelerator | YES (unobserved / unsupported / none found) |
| Heterogeneous multi-provider host | YES (plural devices + provenance) |
